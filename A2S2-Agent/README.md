# A2S2-Agent

A conversational operator for **A2S2-OS**. Instead of tapping a tile to run a
lab task, you can ask the agent in plain words — it finds the right app/mode,
fills the parameters, previews the run, and (after you approve) dispatches it
through the same OS bridge the shell uses.

It is **provider-agnostic**: the same agent runs on **Claude** (default: Claude
Haiku) or on **local / non-local models** through an API key — Ollama or any
OpenAI-compatible endpoint (vLLM, LM Studio, llama.cpp server). Pick the backend
with one env var; the agent loop never changes.

## Why a custom agent (not Claude Code)

The action space here is tiny and already defined by the OS (a handful of
verbs: list apps/modes, describe a mode, run a mode, poll a job). What we need
is a *narrow, locked-down dispatcher* that is genuinely multi-provider and safe
on a kiosk that drives a robot — not a general coding agent. LangGraph +
LangChain gives first-class local-model support and precise control of the tool
set, so that is what this is built on.

## Architecture

```
 user ──► A2S2Agent (LangChain create_agent / ReAct loop)      MCP client
            │   model: make_model() ── Claude|Ollama|OpenAI      (Claude Desktop/Code)
            │                                                          │
        tools.py (LangChain @tool)                            mcp_server.py (MCP)
            └──────────────► os_ops.py ◄──────────────────────────────┘
                   (one shared implementation of every operation)
                     • knowledge:  list_runnables, describe_mode, search_knowledge  ← kg.json
                     • live read:  os_health, list_sessions, job_status             ← A2S2-OS API
                     • run (gated): run_mode  (confirm=false preview / true dispatch) ← POST /api/run
                     • files:       read_file, list_dir, write_file, edit_file       ← fileops.py
                     • code:        run_python, run_shell (any conda env)            ← execops.py
                                            │
                                            ▼
        A2S2-OS bridge (server.py) ──► app job runner ──► twin scripts / other apps
```

- **`run_mode` is the only *hardware*-changing tool.** It will not dispatch
  unless called with `confirm=true`; otherwise it returns a preview to show the
  user. The kiosk policy `A2S2_AGENT_CONFIRM` (default on) enforces this.
- **File & code tools do real data work** — read/write files and run Python or
  shell in any conda env (default: the agent's own; name another for pandas,
  biopython, torch, …). Relative paths resolve under a workspace
  (`A2S2_AGENT_WORKSPACE`, default `<OS root>/workspace`); absolute paths are
  allowed. There is **no sandbox yet** — code runs with the user's privileges;
  a path jail / container is deferred. These tools load only when the agent is
  not read-only (i.e. not in the assistant's `preview`-without-run posture).

## Two ways to run: one-shot vs. persistent chat

- **One-shot** (`cli.py`, `os_ops.run_mode`): a fresh process per message. Simple
  and stateless; conversation continuity comes from `memory.py` replaying a saved
  session. This is what the classic Ask→Watch job flow uses.
- **Persistent chat** (`chat_server.py`): one long-lived agent the OS keeps warm
  for a whole conversation, streaming events over stdio (tokens, tool calls, tool
  results, final). The OS (`server.py`) spawns one per chat session, pipes user
  turns in, and relays events to the browser as **Server-Sent Events**
  (`GET /api/chat/stream`). This backs the in-UI live chat window. Idle chats
  (no SSE client attached) are reaped automatically.

## Knowledge graph (auto-seeded)

`kg.json` is the agent's map of *what the OS can run and which scripts back it*.
It is generated by re-reading each `apps/<id>/app.py` (manifest, modes, full
param specs, and the resolved command template per mode).

**It self-seeds.** Any consumer that reads the KG calls `kg_build.ensure_fresh()`
first, which rebuilds `kg.json` automatically when an OS app is added, removed,
or edited (detected via the `apps/` dir and each `app.py` mtime). So dropping a
new app under `apps/` makes the agent aware of it on its next turn — no manual
step. You can still rebuild explicitly:

```bash
python kg_build.py        # force a rebuild
```

This is what lets the agent answer "what can I run / what does this do / what
flags does it use" accurately instead of guessing.

## Setup

```bash
conda create -n a2s2agent python=3.11 -y
conda activate a2s2agent
pip install -r requirements.txt

# Claude key for the default provider (already present here as .env):
#   ANTHROPIC_API_KEY=sk-ant-...
python env_loader.py      # sanity-check the key (masked)
python kg_build.py        # seed the knowledge graph
```

## Run

```bash
# Interactive
python cli.py

# One-shot
python cli.py "what can I run, and what does the learn mode do?"

# Safe Q&A (run tool disabled), with tool-call trace
python cli.py --read-only --show-tools "is the bench ready?"
```

Embed it:

```python
from agent import A2S2Agent
agent = A2S2Agent()
print(agent.ask("set up a random-play run of 5 episodes, preview only"))
```

## Choosing a model / provider

All via environment (or `.env`):

| Variable | Default | Notes |
|---|---|---|
| `A2S2_AGENT_PROVIDER` | `anthropic` | `anthropic` \| `ollama` \| `openai` |
| `A2S2_AGENT_MODEL` | `claude-haiku-4-5-20251001` | per-provider default if unset |
| `A2S2_OS_URL` | `http://localhost:8770` | the running A2S2-OS |
| `OLLAMA_BASE_URL` | `http://localhost:11434` | for the ollama provider |
| `OPENAI_BASE_URL` | (unset) | set for local OpenAI-compatible servers |
| `A2S2_AGENT_CONFIRM` | `1` | `0` = autonomous (dispatch without confirm) |

Examples:

```bash
# Local model via Ollama
A2S2_AGENT_PROVIDER=ollama A2S2_AGENT_MODEL=llama3.2 python cli.py
# NOTE on local models: tool-calling reliability scales with model size. Small
# models (e.g. llama3.2 3B) often mangle structured tool arguments — the tools
# coerce dict/string/bool variants so they degrade gracefully, but for accurate
# parameter filling prefer a capable tool-use model (qwen2.5-coder:14b tested OK).

# Local OpenAI-compatible server (e.g. vLLM)
A2S2_AGENT_PROVIDER=openai A2S2_AGENT_MODEL=Qwen2.5-14B \
  OPENAI_BASE_URL=http://localhost:8000/v1 python cli.py
```

## MCP server (drive the OS from any MCP client)

The same OS operations are exposed over the **Model Context Protocol** by
`mcp_server.py`, so Claude Desktop, Claude Code, or any other MCP client can list
and run things on the OS *without* going through A2S2-Agent. Both the agent's
LangChain tools and the MCP server call one shared implementation (`os_ops.py`),
so they never drift apart. MCP is model-agnostic — this is the "drive the OS
from anything" seam.

Tools exposed: `list_runnables`, `describe_mode`, `search_knowledge`,
`os_health`, `list_sessions`, `job_status`, `run_mode` (same confirm-gate:
`confirm=false` previews, `confirm=true` dispatches).

Run it (stdio transport, what desktop clients launch):

```bash
python mcp_server.py
```

Register with a client — see `mcp_client_config.example.json` (merge into
`claude_desktop_config.json`), or for Claude Code:

```bash
claude mcp add a2s2-os -- conda run -n a2s2agent \
  python /home/ksa/Models/A2S2-OS_v1.0/A2S2-Agent/mcp_server.py
```

The server needs no API key of its own (the client supplies the model); it only
needs a running A2S2-OS at `A2S2_OS_URL` (default `http://localhost:8770`).

## In-UI integration (apps/assistant)

The agent is wired into A2S2-OS as the app **`assistant`** (name: "AI agent"),
so it appears in the OS app switcher beside the bench tiles. It declares one
mode, **`ask`**, with two parameters:

- **Action** — `preview` (default): the agent answers and previews runs but
  cannot dispatch (it runs `--read-only`, so the run tool isn't even loaded).
  `run`: the agent is authorized to dispatch the mode it chooses.
- **Brain** — which model: `haiku` (default) / `sonnet` / `llama3.2` /
  `qwen-coder`. The app maps each to a provider+model in `apps/assistant/app.py`.
- **Conversation** — `continue` (default) keeps the rolling console
  conversation so follow-ups have context; `new` wipes it before this turn.

The OS runs the agent as a job (`conda run -n a2s2agent python cli.py …`) and
streams its reply into the run log. When the agent dispatches in `run` mode, it
calls back into the same OS via `/api/run` with an explicit `app` target, so the
real work shows up as its own bench job **without changing the active app** (no
flip — the user stays on the assistant view).

**Multi-turn memory.** The OS runs each message as a fresh subprocess, so the
assistant persists a trimmed conversation under `sessions/console.json`
(`memory.py`) and replays it each turn. That makes follow-ups like "ok, do the
third one with 5 episodes" resolve correctly. Only plain user/assistant text is
kept (provider-portable); tool internals are not persisted.
